## Why a baseline exists at all

The ancestor tree was adopted whole (`344176f`), so a large number of failing tests arrived with it.
`build.yml` therefore gates on a *delta*: the `test` and `windows-test` jobs capture vitest output, and
`scripts/known-failures.mjs --check` fails on a failure that is not in the baseline **and** on a baseline entry
that stops failing. Absolute green is not the goal -- a red that is *new* is the signal.

## Regenerating a baseline

A baseline may only be authored from the platform it declares, from a CI log of that platform:

```bash
gh run view <run-id> --repo SeveNOlogy7/oh-my-qoder --log --job <test-job-id> > /tmp/test.log
node scripts/known-failures.mjs --platform=linux \
  --source="run:<run-id>@<sha>" < /tmp/test.log > tests/known-failures-linux.json
node scripts/ci/render-known-failures-doc.mjs --linux=/tmp/test.log --win32=/tmp/win.log \
  --run="<run-id>@<sha>" --write
```

`gh api .../jobs/<id>/logs` returns an empty body here because the response carries escape sequences;
use `gh run view --log --job`. A local Docker run is **not** a substitute for the CI log: `node:20` has no
tmux and no ruby, and the workflow-profile family happens to match CI exactly (114 = 114) while other
families do not. Windows numbers measured on a workstation are not comparable either -- they carry the
same separator noise the windows-latest runner does not.


## What may not be done with this file

Do not regenerate a baseline to make a gate pass. The point of the delta gate is that the set of
tolerated failures only changes when a family's reason changes. If a family above goes green, that
is a *fix*, and the shrink should land in the commit that fixed it, with the family section updated.

The gate itself was verified rather than trusted: feeding a CI log back against a baseline generated
from that same log exits 0 with `Matched: 283`, and deleting one entry from that baseline exits 1
reporting exactly one new failure. So a red gate after a baseline change means a real delta, not a
parser that never matches.

Run-to-run churn was measured rather than assumed, by set-diffing the failure sets of adjacent
runs and asking entry by entry whether the commit in between could have caused it (a `src` change
is attributed to the test files that exercise it):

- `4aca1fe` -> `d2a1a28` (job-id validator + beads-context mock): linux 428 -> 419, every one of the
  25 deltas attributable. win32 1029 -> 1024, with **4 entries starting on their own** --
  `session-start-background-output`, `session-start-script-context`,
  `skill-entitlements-cross-surface`, `tests/lint/inventory-graph-drift`.
- `6ba78e7` -> `4aa3b3b` (workflow-profile fixture env name, test files only): linux 411 -> 283, 127
  of the 128 stops sitting in the two files edited and **1** elsewhere
  (`src/team/__tests__/worker-activation-gate.test.ts > kills recovery provider descendants when the
  root exits immediately`). win32 1016 -> 999 with **7 self-flipping entries**: `session-end-process-exit`
  (one start, one stop), two `state-root-resolution` cases, `run-cjs-graceful-fallback`,
  `runtime-done-recovery`, `workflow-integrity`.

That is ~0.2% of the linux set and ~0.5% of the win32 set per run. Consequence, stated plainly
because it otherwise looks like a broken gate: a windows-test drift naming a handful of files no
commit touched is flake -- re-run the job before treating it as a delta. The same shape is now
possible on linux, just rarer. The files that keep flipping are process-exit, state-root and
worker/recovery timing suites -- the `tmux-worker-timing` family and its neighbours.
